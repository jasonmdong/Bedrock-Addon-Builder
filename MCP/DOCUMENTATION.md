# Mob Forge — Master Documentation

> **A full-stack Minecraft Bedrock Edition mob generator powered by MCP (Model Context Protocol) and LLM-driven code generation.**

Mob Forge lets users describe a custom mob in plain English — "a fire-breathing dragon that drops diamonds" — and produces a fully functional Minecraft Bedrock addon with custom entity behavior, 3D geometry, pixel-art textures, loot tables, and a ready-to-play `.mcworld` file.

## 1. Architecture Overview

The system has three layers connected by two protocols:

```
┌─────────────────────────────────────────────────────────────────────┐
│                        BROWSER (Frontend)                          │
│   Vanilla HTML/CSS/JS  •  Dark theme  •  Glassmorphism UI          │
│   static/index.html  •  static/styles.css  •  static/app.js       │
└───────────────────────────────┬─────────────────────────────────────┘
                                │  HTTP REST (JSON)
                                ▼
┌─────────────────────────────────────────────────────────────────────┐
│                   FastAPI Backend (MCP Client)                      │
│   mob_forge_app/app.py                                             │
│   • Serves the frontend                                            │
│   • Exposes REST endpoints (/api/generate-mob, etc.)               │
│   • Manages in-memory gallery of generated mobs                    │
│   • Spawns MCP server as a subprocess on startup                   │
│   • Translates HTTP requests → MCP tool calls                      │
│   • Translates MCP responses → HTTP JSON responses                 │
└───────────────────────────────┬─────────────────────────────────────┘
                                │  MCP Protocol (stdio transport)
                                │  JSON-RPC over stdin/stdout pipes
                                ▼
┌─────────────────────────────────────────────────────────────────────┐
│                    MCP Server (Tool Provider)                       │
│   mcp_server/server.py  (FastMCP)                                  │
│   • Registers 5 tools                                              │
│   • Each tool delegates to a module in mcp_server/tools/           │
│   • Tools call GitHub Models API (OpenAI-compatible) for LLM       │
│   • Tools generate Bedrock-compatible JSON, PNG, and ZIP files     │
└─────────────────────────────────────────────────────────────────────┘
```

### Key Design Decisions

- **MCP as the tool layer**: The MCP server is a standalone process that exposes tools via the Model Context Protocol. This means the same tools can be consumed by the FastAPI web app, VS Code Copilot (via `.vscode/mcp.json`), or any MCP-compatible client.
- **stdio transport**: The MCP server communicates over stdin/stdout pipes (JSON-RPC). The FastAPI app spawns it as a subprocess and manages the bidirectional stream.
- **LLM-driven generation**: Entity behavior, 3D geometry, and textures are all generated by an LLM (GPT-4o-mini by default via GitHub Models). Each tool has a carefully engineered system prompt with Bedrock format documentation, examples, and validation rules.
- **In-memory gallery**: Generated mobs are stored in a Python dict keyed by UUID. This allows the frontend to display all mobs and selectively build packs from them.

## 3. The MCP Connection

### What is MCP?

**Model Context Protocol (MCP)** is an open protocol that lets AI applications (clients) discover and call tools hosted by separate processes (servers). It uses JSON-RPC over a transport layer (stdio in our case).

### How Mob Forge Uses MCP

#### Server Side (`mcp_server/server.py`)

The MCP server uses the `FastMCP` library to register 5 tools. Each tool is a Python async function decorated with `@mcp.tool()`:

```python
from mcp.server.fastmcp import FastMCP
mcp = FastMCP("Mob Forge")

@mcp.tool()
async def generate_mob(description: str, difficulty: str = "medium") -> str:
    ...
```

The server runs on **stdio transport** — it reads JSON-RPC requests from stdin and writes responses to stdout. This is launched by:

```python
if __name__ == "__main__":
    mcp.run()
```

#### Client Side (`mob_forge_app/app.py`)

The FastAPI app acts as an **MCP client**. On startup, it:

1. **Spawns** the MCP server as a subprocess using `StdioServerParameters`:
   ```python
   server_params = StdioServerParameters(
       command=sys.executable,        # python
       args=[server_path],            # mcp_server/server.py
       env={**os.environ},            # passes GITHUB_TOKEN, model env vars
       cwd=server_dir,                # mcp_server/
   )
   ```

2. **Connects** via `stdio_client()` which creates read/write streams to the subprocess pipes:
   ```python
   _mcp_context = stdio_client(server_params)
   _mcp_read, _mcp_write = await _mcp_context.__aenter__()
   ```

3. **Initializes** a `ClientSession` over those streams:
   ```python
   mcp_session = ClientSession(_mcp_read, _mcp_write)
   await mcp_session.__aenter__()
   await mcp_session.initialize()
   ```

4. **Verifies** the connection by listing available tools:
   ```python
   tools = await mcp_session.list_tools()
   # Output: ['generate_mob', 'build_mob_pack', 'generate_mob_texture', 'build_mcworld', 'generate_mob_geometry']
   ```

#### Calling Tools

Every REST endpoint translates to an MCP `call_tool`:

```python
result = await mcp_session.call_tool("generate_mob", {
    "description": "a fire-breathing dragon",
    "difficulty": "hard"
})
```

The MCP response is a `CallToolResult` with a list of content blocks. The app extracts the text content, parses it as JSON, and returns it as an HTTP response.

#### VS Code / Copilot Integration

The `.vscode/mcp.json` file lets VS Code Copilot Agent mode use the same MCP server directly:

```json
{
  "servers": {
    "mob-forge": {
      "type": "stdio",
      "command": "python",
      "args": ["mcp_server/server.py"]
    }
  }
}
```

This means Copilot can call `generate_mob`, `build_mob_pack`, etc. as tools during a conversation.

## 4. Pipeline Flows

### 4.1 Mob Generation Pipeline

**Endpoint**: `POST /api/generate-mob`
**MCP Tool**: `generate_mob`
**LLM Model**: Configurable via `MOB_FORGE_MOB_MODEL` (default: `gpt-4o-mini`)

```
User prompt: "a fire-breathing dragon that drops diamonds"
    │
    ▼
┌─ FastAPI (app.py) ──────────────────────────────────────────────────┐
│  1. Receive POST with {description, difficulty}                     │
│  2. call_tool("generate_mob", {...})                                │
│     │                                                               │
│     ▼                                                               │
│  ┌─ MCP Server → generate_mob.py ─────────────────────────────────┐ │
│  │  3. Build user prompt with description + difficulty             │ │
│  │  4. Call GitHub Models API (GPT-4o-mini) with:                  │ │
│  │     - GENERATE_MOB_SYSTEM_PROMPT (from bedrock_reference.py)    │ │
│  │     - Contains: valid components, behavior patterns, examples,  │ │
│  │       difficulty presets, loot drop format, scale guidance       │ │
│  │  5. Parse LLM JSON response                                    │ │
│  │  6. Extract _mob_forge_style → style for 3D model mapping      │ │
│  │  7. Extract _mob_forge_loot → item drops for loot table        │ │
│  │  8. Wire minecraft:loot component to loot table path            │ │
│  │  9. validate_mob_json() — fix format_version, clamp stats,     │ │
│  │     ensure essential components, fix identifier namespace       │ │
│  │  10. extract_metadata() — read HP, ATK, SPD from components,   │ │
│  │      detect abilities, guess colors from description,           │ │
│  │      determine visual style                                     │ │
│  │  11. Return {entity, metadata, status}                          │ │
│  └─────────────────────────────────────────────────────────────────┘ │
│                                                                      │
│  12. Store in gallery[mob_id] = {entity, metadata, ...}             │
│  13. Auto-call generate_mob_geometry (see 4.2)                      │
│  14. Auto-call generate_mob_texture (see 4.3)                       │
│  15. Return full mob data to frontend                                │
└──────────────────────────────────────────────────────────────────────┘
```

**Key Data Produced:**

| Field | Source | Example |
|-------|--------|---------|
| `entity` | LLM + validation | Full Bedrock entity JSON with components |
| `metadata.display_name` | Extracted from identifier | "Fire Dragon" |
| `metadata.hp` | From `minecraft:health.value` | 200 |
| `metadata.attack` | From `minecraft:attack.damage` | 30 |
| `metadata.speed` | From `minecraft:movement.value` | 0.4 |
| `metadata.abilities` | Detected from components | ["Flight", "Fire Immune", "Ranged Attack"] |
| `metadata.suggested_style` | LLM's `_mob_forge_style` or heuristic | "phantom" |
| `metadata.suggested_colors` | Keyword matching from description | ["#AA2200", "#FF6600", "#331100"] |
| `metadata.loot_drops` | LLM's `_mob_forge_loot` | [{item: "minecraft:diamond", ...}] |

### 4.2 Geometry Generation Pipeline

**MCP Tool**: `generate_mob_geometry`
**LLM Model**: Configurable via `MOB_FORGE_GEOMETRY_MODEL` (default: `gpt-4o-mini`)

```
Input: mob_name, description, collision_width, collision_height
    │
    ▼
┌─ generate_geometry.py ────────────────────────────────────────────────┐
│  1. Convert collision dimensions to geometry units (×16)              │
│     collision_height=3.0 → 48 units (3 blocks tall)                  │
│  2. Build user message with explicit size requirements               │
│  3. Call LLM with GEOMETRY_SYSTEM_PROMPT containing:                 │
│     - Bedrock geometry format spec (format_version "1.12.0")         │
│     - Coordinate system (Y=up, ground=Y=0, 16 units = 1 block)      │
│     - Box UV mapping rules                                           │
│     - Design rules (body bone required, blocky cubes, etc.)          │
│     - Size tiers (tiny=6-10, small=10-16, medium=16-24,             │
│       large=24-32, very large=36-64 units)                           │
│     - Full examples (quadruped, dragon, spider, humanoid)            │
│  4. Parse JSON response                                              │
│  5. validate_geometry() — ensure identifier prefix, texture dims,    │
│     bone existence, body bone presence                               │
│  6. Return {geometry, geometry_id, texture_width, texture_height,    │
│     bone_count}                                                      │
└───────────────────────────────────────────────────────────────────────┘
```

**Output Example (simplified):**
```json
{
  "format_version": "1.12.0",
  "minecraft:geometry": [{
    "description": {
      "identifier": "geometry.fire_dragon",
      "texture_width": 64,
      "texture_height": 64
    },
    "bones": [
      {"name": "body", "pivot": [0, 12, 0], "cubes": [...]},
      {"name": "head", "parent": "body", ...},
      {"name": "wing_left", "parent": "body", ...},
      {"name": "wing_right", "parent": "body", ...},
      {"name": "tail", "parent": "body", ...},
      {"name": "leg_front_left", "parent": "body", ...}
    ]
  }]
}
```

### 4.3 Texture Generation Pipeline

**MCP Tool**: `generate_mob_texture`
**LLM Model**: Configurable via `MOB_FORGE_TEXTURE_MODEL` (default: `gpt-4o-mini`)

```
Input: mob_name, description, style, colors, size
    │
    ▼
┌─ generate_texture.py ─────────────────────────────────────────────────┐
│  1. Look up correct texture dimensions from STYLE_TEXTURE_SIZE       │
│     (e.g., "zombie" → 64×64, "cow" → 64×32)                        │
│  2. Try AI-generated texture:                                        │
│     a. Build prompt with GENERATE_TEXTURE_SYSTEM_PROMPT              │
│        - UV layout rules per body type (humanoid, quadruped, etc.)   │
│        - Color palette usage rules                                   │
│        - Eye placement guidance                                      │
│     b. Call LLM → parse pixel grid JSON                              │
│     c. Validate grid dimensions match expected size                  │
│  3. If AI fails → algorithmic fallback:                              │
│     generate_algorithmic_texture() creates body-plan-aware           │
│     patterns (humanoid, quadruped, flying, spider, slime, aquatic)   │
│  4. render_grid_to_png() — convert hex color grid to PNG bytes       │
│  5. Base64-encode the PNG                                            │
│  6. Return {texture_base64, width, height, style, ai_generated}     │
└───────────────────────────────────────────────────────────────────────┘
```

**Fallback System**: The texture pipeline has a robust two-tier approach:
- **Tier 1 (AI)**: LLM generates a pixel grid as a JSON 2D array of hex colors
- **Tier 2 (Algorithmic)**: If LLM fails or returns wrong dimensions, a deterministic algorithm generates a texture based on the body style family (humanoid, quadruped, flying, spider, slime, aquatic) with proper UV region placement.

### 4.5 World Build Pipeline (.mcworld)

**MCP Tool**: `build_mcworld`
**File**: `build_mcworld.py`

This is the most complex pipeline. It creates a complete playable Minecraft world.

```
Input: list of mobs, pack_name
    │
    ▼
┌─ .mcworld ZIP Structure ──────────────────────────────────────────────┐
│                                                                       │
│  level.dat / level.dat_old                                           │
│  ├── Little-endian NBT with 8-byte header                            │
│  ├── Creative mode, cheats enabled, flat world generator              │
│  ├── Experiments: none (vanilla-compatible)                           │
│  └── Written by custom Python NBT writer (no external lib needed)    │
│                                                                       │
│  world_behavior_packs.json   — References the embedded BP             │
│  world_resource_packs.json   — References the embedded RP             │
│                                                                       │
│  db/CURRENT                  — Empty LevelDB (Minecraft regenerates)  │
│                                                                       │
│  behavior_packs/<name>_BP/                                           │
│  ├── manifest.json                                                    │
│  ├── pack_icon.png                                                    │
│  ├── entities/<mob>.json          — Entity behavior definition        │
│  ├── loot_tables/entities/<mob>.json — Loot tables for drops         │
│  └── functions/                                                       │
│      ├── tick.json                — Runs startup.mcfunction every tick │
│      └── startup.mcfunction       — One-shot mob summon logic         │
│                                                                       │
│  resource_packs/<name>_RP/                                           │
│  ├── manifest.json                                                    │
│  ├── pack_icon.png                                                    │
│  ├── texts/en_US.lang                                                │
│  ├── entity/<mob>.entity.json     — Client entity definition          │
│  ├── textures/entity/<mob>.png    — Mob texture                       │
│  └── models/entity/<mob>.geo.json — Custom 3D geometry                │
│                                                                       │
└───────────────────────────────────────────────────────────────────────┘
```

#### The NBT Writer

Bedrock's `level.dat` uses **little-endian Named Binary Tag (NBT)** format with an 8-byte header (4-byte version + 4-byte payload length). The `build_mcworld.py` file contains a complete custom NBT writer that handles all tag types (Byte, Short, Int, Long, Float, Double, String, ByteArray, IntArray, Compound, List) without any external NBT library.

#### One-Shot Mob Summon System

The `.mcworld` does **not** use spawn rules (which would cause mobs to spawn randomly everywhere). Instead, it uses a **scoreboard-gated one-shot mcfunction**:

```mcfunction
# startup.mcfunction — called every tick via tick.json
scoreboard objectives add mobforge_init dummy

# Gate: only runs if (a) a player exists AND (b) flag not yet set
execute unless score mfinit mobforge_init matches 1.. as @p at @s run summon custom:fire_dragon ~2 ~ ~2
execute unless score mfinit mobforge_init matches 1.. run tellraw @a {"rawtext":[{"text":"§aMob Forge: §fCustom mobs summoned near you!"}]}

# Set flag so it never runs again (but only if player exists)
execute if entity @a run scoreboard players set mfinit mobforge_init 1
```

**How it works:**
1. `tick.json` calls `startup` every game tick
2. `scoreboard objectives add` is idempotent — safe to run repeatedly
3. `execute unless score mfinit mobforge_init matches 1..` — only runs if score is NOT ≥1
4. `as @p at @s run` — executes at the nearest player's position
5. After summoning, sets score to 1 → never runs again
6. `execute if entity @a` — prevents the flag from being set before any player loads

## 7. Bedrock Addon Structure

### Entity Behavior JSON (`entities/<mob>.json`)

The entity JSON follows Bedrock format_version `1.16.0` and contains:

- **`description`**: Identifier (`custom:<mob_name>`), spawn/summon flags
- **`components`**: All behavior and stats
  - `minecraft:health` — HP value and max
  - `minecraft:attack` — Melee damage
  - `minecraft:movement` — Walk speed
  - `minecraft:collision_box` — Physical hitbox dimensions
  - `minecraft:scale` — Visual scale multiplier (e.g., 2.5 for elephants)
  - `minecraft:loot` — Path to loot table for drops
  - `minecraft:behavior.*` — AI behaviors (targeting, attacking, wandering, etc.)
  - `minecraft:navigation.*` — Pathfinding (walk, fly, swim)
  - `minecraft:movement.*` — Movement type (basic, fly, sway)
  - Special: `minecraft:shooter`, `minecraft:fire_immune`, `minecraft:explode`, `minecraft:area_attack`

### Client Entity JSON (`entity/<mob>.entity.json`)

Links the behavior entity to visual resources:
- **Materials**: `entity_alphatest` (supports transparency)
- **Textures**: Points to `textures/entity/<mob>`
- **Geometry**: Points to `geometry.<mob_name>` (custom) or vanilla geometry
- **Render Controllers**: `controller.render.default`
- **Spawn Egg**: Color-coded for the mob

### Geometry JSON (`models/entity/<mob>.geo.json`)

Custom 3D model using Bedrock format_version `1.12.0`:
- **Bones**: Hierarchical body parts (body → head, legs, tail, wings, etc.)
- **Cubes**: Rectangular boxes with origin, size, and UV coordinates
- **Box UV**: Automatic face UV mapping from a single [u,v] coordinate
- **Scale**: 16 geometry units = 1 Minecraft block

### Style Mapping System

The system maps each mob to a "style" that determines:

| Style | Geometry | Collision Box | Texture Size |
|-------|----------|---------------|--------------|
| zombie | geometry.zombie | 0.6 × 1.9 | 64×64 |
| cow | geometry.cow | 0.9 × 1.4 | 64×32 |
| phantom | geometry.phantom | 0.9 × 0.5 | 64×64 |
| spider | geometry.spider | 1.4 × 0.9 | 64×32 |
| slime | geometry.slime | 0.6 × 0.6 | 64×32 |
| polar_bear | geometry.polar_bear | 1.3 × 1.4 | 128×64 |
| ... | (30+ styles total) | ... | ... |

With custom geometry generation, the style is used primarily for texture UV layout and fallback purposes. The actual 3D model is generated uniquely per mob.

## 9. Issues, Challenges & Fixes

### Challenge 1: MCP Session Management

**Problem**: The MCP protocol uses a persistent bidirectional stream. The FastAPI app needed to spawn the MCP server subprocess, maintain the stdio pipes, and keep the session alive across all HTTP requests.

**Fix**: Used the `@asynccontextmanager` lifespan pattern in FastAPI. On startup, `connect_mcp()` spawns the subprocess and initializes the session. On shutdown, `disconnect_mcp()` cleanly closes both the session and the subprocess context manager. The session is stored as a module-level global `mcp_session` and reused for all `call_tool()` invocations.

### Challenge 2: LLM Output Parsing

**Problem**: LLMs frequently wrap JSON in markdown code fences (` ```json ... ``` `), add commentary before/after the JSON, or produce slightly malformed output.

**Fix**: Every tool has a multi-step parsing pipeline:
1. Strip markdown code fences (```` ``` ````)
2. Regex extract the outermost `{...}` block
3. `json.loads()` with error reporting
4. Post-parse validation specific to each tool

### Challenge 3: Mobs Spawning Randomly Everywhere

**Problem**: The `.mcworld` originally included `spawn_rules` JSON files with `weight: 80` and surface spawn conditions. This caused dozens of copies of the custom mob to spawn all over the world like hostile mobs.

**Root Cause**: Spawn rules are Bedrock's natural mob spawning system. They're designed for vanilla mobs like zombies that should spawn naturally. Custom mobs should only appear once, near the player.

**Fix**: 
1. **Removed** all `spawn_rules` from the `.mcworld` behavior pack
2. **Implemented** a one-shot scoreboard-gated summon system using `startup.mcfunction` + `tick.json`
3. The function runs every tick but is gated by a scoreboard score — once it fires, it sets the flag and never runs again

### Challenge 4: Bedrock Execute Command Syntax

**Problem**: The initial mcfunction used old Java Edition execute syntax (`execute @p ~ ~ ~`) and quoted fake player names (`"init"`), which Bedrock doesn't support.

**Root Cause**: Bedrock Edition 1.19.50+ uses a different execute command syntax than Java Edition. The old syntax `execute <entity> <pos> <command>` was replaced with `execute as <target> at @s run <command>`.

**Fix**: Rewrote all execute commands to use correct Bedrock syntax:
- Old: `execute @p ~ ~ ~ summon custom:mob ~2 ~ ~2`
- New: `execute as @p at @s run summon custom:mob ~2 ~ ~2`
- Old: `execute unless score "init" mobforge_init matches 1..`
- New: `execute unless score mfinit mobforge_init matches 1..`

### Challenge 5: Mobs Not Spawning (Timing Issue)

**Problem**: Even with the scoreboard system, mobs never appeared. The summon commands ran before any player loaded into the world.

**Root Cause**: `tick.json` fires on the very first game tick, before any player entity exists. The scoreboard flag was being set unconditionally on tick 1, so by the time the player loaded, the "already spawned" flag was already set.

**Fix**: Added `execute if entity @a` gate to every command, including the flag setter:
```mcfunction
# Won't run until a player actually exists
execute unless score mfinit mobforge_init matches 1.. as @p at @s run summon custom:mob ~2 ~ ~2
# Flag only set if player exists
execute if entity @a run scoreboard players set mfinit mobforge_init 1
```

### Challenge 6: All Mobs Had Identical Green Textures

**Problem**: Elephant and giraffe both had the same green placeholder texture, despite having different descriptions and colors.

**Root Cause**: Texture generation was never called automatically during mob creation. The `api_generate_mob` endpoint only called `generate_mob` (entity) and returned — the texture was left as `null`, and the build pipeline fell back to a green default.

**Fix**: Added auto-texture generation in `app.py`'s `api_generate_mob` endpoint, right after geometry generation:
```python
tex_result = await call_tool("generate_mob_texture", {
    "mob_name": metadata.get("display_name", mob_name),
    "description": req.description,
    "style": metadata.get("suggested_style", "zombie"),
    "colors": metadata.get("suggested_colors", [...]),
})
```

### Challenge 7: All Mobs Were the Same Small Size

**Problem**: An elephant, giraffe, and rabbit all appeared as roughly the same size in-game, despite the descriptions requesting different sizes.

**Root Cause**: Two issues:
1. The geometry prompt's scale guidance was incorrect — it said "large is ~20-32 units" which is only 1.2-2 blocks (too small for an elephant).
2. The entity prompt didn't emphasize the `minecraft:scale` component, so the LLM rarely included it.

**Fix**:
1. **Updated geometry prompt** with correct scale: "16 units = 1 block. Player = 32 units. Elephant = 40-48 units. Giraffe = 56-64 units."
2. **Updated entity prompt** to require `minecraft:scale` with specific guidelines:
   - Large mobs (elephant): `scale: 2.5`, collision `2.0 × 3.0`
   - Very large mobs (dragon): `scale: 2.5+`, collision `2.5 × 3.5`
3. **Passed collision dimensions** from entity JSON to geometry generation so the 3D model is proportional

### Challenge 8: Color Detection for Common Animals

**Problem**: "Elephant" didn't match any color keyword so it defaulted to green (`#4A7023`). Different animals with distinct colors got the same default palette.

**Fix**: Expanded the color hints dictionary from ~20 entries to 60+ entries covering:
- **Animals**: elephant (grey), giraffe (golden), lion (tawny), tiger (orange/black), panda (white/black), etc.
- **Elements**: fire (red/orange), ice (light blue), shadow (dark purple), lava (orange), crystal (purple), etc.
- **Colors**: red, blue, purple, gold, etc.
- Changed the default fallback from green to grey (`#808080`)

### Challenge 9: Mob Behaviors Non-Functional

**Problem**: Generated mobs stood still, didn't attack, didn't drop items, and had no special abilities (e.g., "fire-breathing dragon" couldn't breathe fire).

**Root Cause**: The entity generation prompt only had basic zombie/creeper examples. It didn't include:
1. Complete hostile AI behavior chains
2. Shooter/projectile components for fire breathing
3. Loot table references for item drops
4. Proper behavior priorities

**Fix**: Major prompt overhaul in `bedrock_reference.py`:
1. **Added behavior pattern templates** for hostile, passive, ranged, exploding, and area-attack mobs
2. **Added `_mob_forge_loot` system**: LLM specifies item drops in a custom key, which is extracted and converted to Bedrock loot tables during pack building
3. **Added loot table generation** to both `build_mob_pack.py` and `build_mcworld.py`
4. **Wired `minecraft:loot` component** in entity JSON to reference the generated loot table path

### Challenge 10: GitHub Models Rate Limiting

**Problem**: Hit the 50 requests/day limit on GPT-4o. Since each mob generation makes 3 LLM calls (entity + geometry + texture), users could only create ~17 mobs per day.

**Fix**:
1. Switched all tools to `gpt-4o-mini` (150 requests/day, separate quota)
2. Made model selection configurable via `.env` with per-tool overrides
3. Users can switch to `gpt-4o` for higher quality or `gpt-4o-mini` for higher throughput

## 10. Tech Stack

| Layer | Technology | Purpose |
|-------|-----------|---------|
| **MCP Server** | Python + FastMCP | Tool hosting via stdio transport |
| **LLM** | GitHub Models (GPT-4o-mini) | Entity, geometry, and texture generation |
| **Web Backend** | FastAPI + uvicorn | REST API + MCP client |
| **MCP Client** | `mcp.client.stdio` | Subprocess management + JSON-RPC |
| **Web Frontend** | Vanilla HTML/CSS/JS | Dark theme, glassmorphism UI |
| **Image Generation** | Pillow (PIL) | Render pixel grids to PNG textures |
| **NBT Writing** | Custom Python | Little-endian NBT for level.dat |
| **Pack Building** | Python zipfile | .mcpack and .mcworld ZIP creation |
| **Config** | python-dotenv | .env file loading |

## Running the Application

```bash
# 1. Install dependencies
pip install -r mob_forge_app/requirements.txt

# 2. Set up environment
cp .env.example .env
# Edit .env with your GitHub PAT

# 3. Start the server
python -m uvicorn mob_forge_app.app:app --host 0.0.0.0 --port 8000

# 4. Open http://localhost:8000 in your browser
```

The FastAPI app will automatically spawn the MCP server subprocess and connect to it. You should see:

```
[MobForge] Connected to MCP server. Tools: ['generate_mob', 'build_mob_pack', 'generate_mob_texture', 'build_mcworld', 'generate_mob_geometry']
```
